# 需求分析框架

## 需求分析的目标

需求分析是将用户痛点和业务目标转化为清晰、可执行的产品需求的过程。

**核心任务:**
- 识别和收集需求
- 分析需求优先级
- 验证需求合理性
- 定义需求边界

## KANO 模型

KANO 模型将需求分为五类,帮助确定优先级:

### 需求分类

| 类型 | 说明 | 示例 | 优先级 |
| --- | --- | --- | --- |
| **基本型需求** | 必须有,没有会不满 | 电商平台能下单 | 高 |
| **期望型需求** | 越好越满意 | 配送速度快 | 中 |
| **兴奋型需求** | 超出预期的惊喜 | 免费赠品 | 低 |
| **无差异需求** | 有没有都无所谓 | 某些装饰功能 | 忽略 |
| **反向型需求** | 有了反而不满 | 过多的广告 | 避免 |

### 使用方法

1. **列出所有需求**
2. **设计 KANO 问卷**
   ```
   问题1: 如果产品有 [功能X],您的感受?
   A. 我喜欢
   B. 理应如此
   C. 无所谓
   D. 我能接受
   E. 我不喜欢
   
   问题2: 如果产品没有 [功能X],您的感受?
   A. 我喜欢
   B. 理应如此
   C. 无所谓
   D. 我能接受
   E. 我不喜欢
   ```

3. **分析结果,确定需求类型**
4. **优先实现基本型和期望型需求**

## MoSCoW 优先级法

将需求分为四个优先级:

| 优先级 | 含义 | 说明 |
| --- | --- | --- |
| **Must have** | 必须有 | 没有无法上线,P0 需求 |
| **Should have** | 应该有 | 重要但可延后,P1 需求 |
| **Could have** | 可以有 | 锦上添花,P2 需求 |
| **Won't have** | 不会有 | 本期不做,未来可能考虑 |

**示例:**

```markdown
## 用户管理模块

### Must have (P0)
- 用户注册
- 用户登录
- 密码加密存储

### Should have (P1)
- 找回密码
- 修改个人信息
- 头像上传

### Could have (P2)
- 第三方登录 (微信、QQ)
- 账号注销
- 登录历史记录

### Won't have
- 人脸识别登录
- 多账号切换
```

## RICE 评分模型

量化评估需求价值,适合有大量需求时排序。

**公式:** RICE = (Reach × Impact × Confidence) / Effort

| 维度 | 说明 | 评分 |
| --- | --- | --- |
| **Reach** | 影响用户数 | 每季度影响的用户数 |
| **Impact** | 影响程度 | 3=巨大, 2=高, 1=中, 0.5=低, 0.25=微小 |
| **Confidence** | 信心程度 | 100%=高, 80%=中, 50%=低 |
| **Effort** | 工作量 | 人月数 |

**示例:**

| 需求 | Reach | Impact | Confidence | Effort | RICE | 排序 |
| --- | --- | --- | --- | --- | --- | --- |
| 搜索功能 | 10000 | 3 | 100% | 2 | 15000 | 1 |
| 收藏功能 | 5000 | 2 | 80% | 1 | 8000 | 2 |
| 分享功能 | 3000 | 1 | 50% | 0.5 | 3000 | 3 |

## 需求分析流程

### 1. 需求收集

**来源:**
- 用户反馈 (客服、调研、访谈)
- 数据分析 (用户行为、流失原因)
- 竞品分析 (竞品功能、市场趋势)
- 业务目标 (公司战略、KPI)
- 团队头脑风暴

**收集工具:**
- 需求池 (Excel、Notion、JIRA)
- 用户反馈平台
- 数据分析平台

### 2. 需求筛选

**筛选标准:**

```markdown
## 需求评估清单

### 必要性
- [ ] 是否解决真实用户痛点?
- [ ] 是否符合产品定位?
- [ ] 是否支持业务目标?

### 可行性
- [ ] 技术上能实现吗?
- [ ] 资源是否充足?
- [ ] 时间是否允许?

### 价值性
- [ ] 影响多少用户?
- [ ] 能带来多大价值?
- [ ] ROI 如何?

### 风险性
- [ ] 有什么潜在风险?
- [ ] 是否有依赖?
- [ ] 失败成本多大?
```

### 3. 需求分析

**分析维度:**

1. **用户价值**
   - 解决什么问题?
   - 为用户带来什么价值?
   - 用户愿意为此付费吗?

2. **商业价值**
   - 能增加收入吗?
   - 能降低成本吗?
   - 能提升品牌吗?

3. **技术可行性**
   - 现有技术能实现吗?
   - 需要多少开发时间?
   - 有什么技术风险?

4. **竞争优势**
   - 竞品有这个功能吗?
   - 我们能做得更好吗?
   - 是否是差异化优势?

### 4. 需求拆解

**大需求拆解为小需求:**

```markdown
## 需求: 用户管理系统

### 一级需求
1. 用户注册登录
2. 用户信息管理
3. 权限管理

### 二级需求
1. 用户注册登录
   1.1 手机号注册
   1.2 邮箱注册
   1.3 密码登录
   1.4 验证码登录
   1.5 找回密码

2. 用户信息管理
   2.1 查看个人信息
   2.2 修改个人信息
   2.3 上传头像
   2.4 修改密码

3. 权限管理
   3.1 角色定义
   3.2 权限分配
   3.3 权限验证
```

### 5. 需求排序

**综合考虑:**
- 业务价值
- 用户价值
- 实现成本
- 技术依赖
- 战略重要性

**排序方法:**
1. 使用 RICE 模型量化评分
2. 使用 MoSCoW 分类
3. 团队讨论达成共识

## 需求文档化

**需求描述模板:**

```markdown
### 需求ID: REQ-001

**需求名称:** 用户手机号注册

**需求类型:** 功能需求

**优先级:** P0 (Must have)

**需求来源:** 用户调研 (80% 用户希望支持手机号注册)

**需求描述:**
用户可以使用手机号注册账号,通过短信验证码验证身份。

**用户故事:**
作为一个新用户,我希望能用手机号快速注册,这样我不需要记住复杂的用户名。

**验收标准:**
- [ ] 用户可以输入手机号
- [ ] 系统发送验证码到手机
- [ ] 用户输入正确验证码后注册成功
- [ ] 注册成功后自动登录
- [ ] 验证码 5 分钟内有效
- [ ] 同一手机号每天最多发送 5 次验证码

**依赖:**
- 短信服务商接口

**风险:**
- 短信服务商故障导致无法注册

**工作量评估:** 3 人日

**负责人:** 张三

**计划上线时间:** 2024-02-01
```

## 需求评审

**评审参与者:**
- 产品经理 (主持)
- 研发负责人
- 设计负责人
- 测试负责人
- 相关业务方

**评审内容:**
- [ ] 需求是否清晰?
- [ ] 优先级是否合理?
- [ ] 验收标准是否明确?
- [ ] 技术方案是否可行?
- [ ] 工作量评估是否准确?
- [ ] 是否有遗漏的场景?
- [ ] 是否有更好的方案?

**评审产出:**
- 需求确认或修改
- 技术方案初步讨论
- 工作量评估
- 排期计划

## 需求变更管理

**变更流程:**

1. **提出变更**
   - 说明变更原因
   - 评估变更影响

2. **评审变更**
   - 技术可行性
   - 工作量变化
   - 排期影响

3. **决策变更**
   - 接受: 更新需求文档和排期
   - 拒绝: 记录原因,延后处理
   - 延期: 下个版本考虑

4. **通知相关方**
   - 更新需求文档
   - 同步团队

## 常见陷阱

❌ **避免:**
- 需求过于宽泛,边界不清
- 只凭直觉,不做数据分析
- 优先级全是 P0
- 需求频繁变更
- 忽视技术可行性

✅ **推荐:**
- 需求清晰、可量化
- 数据驱动决策
- 合理的优先级分布
- 需求变更有流程
- 与研发充分沟通
