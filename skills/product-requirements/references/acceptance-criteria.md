# 验收标准定义

## 什么是验收标准

验收标准 (Acceptance Criteria) 是判断需求是否完成的明确标准,回答"怎样才算做完了"这个问题。

**作用:**
- 明确需求边界
- 指导开发和测试
- 避免理解偏差
- 验收依据

## 验收标准的特征

好的验收标准应该是 **SMART** 的:

| 特征 | 说明 | 示例 |
| --- | --- | --- |
| **Specific** | 具体明确 | "支持手机号注册" 而非 "支持注册" |
| **Measurable** | 可衡量 | "响应时间 < 200ms" 而非 "速度快" |
| **Achievable** | 可实现 | 考虑技术和资源限制 |
| **Relevant** | 相关的 | 与需求目标直接相关 |
| **Time-bound** | 有时限 | 明确验收时间点 |

## 编写格式

### Given-When-Then 格式

适合描述用户行为和系统响应:

```markdown
**场景:** 用户手机号注册

**Given** (前置条件)
- 用户未注册过
- 手机号有效

**When** (触发动作)
- 用户输入手机号和密码
- 用户输入验证码
- 用户点击"注册"按钮

**Then** (预期结果)
- 系统创建新账号
- 系统发送欢迎邮件
- 用户自动登录
- 跳转到首页
```

### Checklist 格式

适合功能点验收:

```markdown
## 用户注册功能验收标准

### 功能完整性
- [ ] 支持手机号注册
- [ ] 支持邮箱注册
- [ ] 发送验证码
- [ ] 验证码校验
- [ ] 密码强度校验
- [ ] 注册成功后自动登录

### 性能要求
- [ ] 注册接口响应时间 < 200ms (P95)
- [ ] 验证码 60 秒内送达
- [ ] 支持 1000 并发注册

### 安全要求
- [ ] 密码 bcrypt 加密存储
- [ ] 防止 SQL 注入
- [ ] 防止 XSS 攻击
- [ ] 同一手机号每天最多 5 次验证码

### 异常处理
- [ ] 手机号已注册 → 提示"该手机号已注册"
- [ ] 验证码错误 → 提示"验证码错误"
- [ ] 验证码过期 → 提示"验证码已过期"
- [ ] 网络异常 → 提示"网络异常,请重试"

### 兼容性
- [ ] iOS 13+ 正常使用
- [ ] Android 8+ 正常使用
- [ ] Chrome/Safari/Firefox 最新两个版本

### 用户体验
- [ ] 表单校验实时反馈
- [ ] 验证码倒计时显示
- [ ] 密码可显示/隐藏
- [ ] 操作流程顺畅,无卡顿
```

## 不同类型需求的验收标准

### 功能需求

```markdown
## 功能: 搜索商品

### 验收标准
- [ ] 用户可以输入关键词搜索
- [ ] 搜索结果按相关度排序
- [ ] 支持商品名称、品牌、分类搜索
- [ ] 搜索结果显示商品图片、名称、价格
- [ ] 无结果时显示"未找到相关商品"
- [ ] 搜索历史记录保存最近 10 条
- [ ] 支持搜索结果筛选 (价格、品牌、分类)
```

### 性能需求

```markdown
## 性能验收标准

### 响应时间
- [ ] 首页加载时间 < 2 秒
- [ ] API 响应时间 < 200ms (P95)
- [ ] 搜索结果返回 < 500ms

### 并发能力
- [ ] 支持 10,000 并发用户
- [ ] 支持 1,000 QPS

### 资源使用
- [ ] CPU 使用率 < 70%
- [ ] 内存使用率 < 80%
- [ ] 数据库连接数 < 100
```

### 安全需求

```markdown
## 安全验收标准

### 数据安全
- [ ] 密码加密存储 (bcrypt)
- [ ] 敏感数据传输加密 (HTTPS)
- [ ] 用户数据访问权限控制

### 攻击防护
- [ ] SQL 注入测试通过
- [ ] XSS 攻击测试通过
- [ ] CSRF 防护测试通过
- [ ] 暴力破解防护 (登录失败 5 次锁定 30 分钟)

### 合规性
- [ ] 符合 GDPR 数据保护要求
- [ ] 用户数据可导出
- [ ] 用户数据可删除
```

### UI/UX 需求

```markdown
## UI/UX 验收标准

### 视觉设计
- [ ] 符合设计稿 (误差 < 2px)
- [ ] 颜色、字体、间距符合设计规范
- [ ] 图标清晰,尺寸正确

### 交互体验
- [ ] 按钮点击有反馈 (颜色变化/动画)
- [ ] 加载时显示 loading 动画
- [ ] 操作成功/失败有明确提示
- [ ] 表单校验实时反馈

### 响应式设计
- [ ] 手机端 (375px-428px) 显示正常
- [ ] 平板端 (768px-1024px) 显示正常
- [ ] 桌面端 (1280px+) 显示正常

### 可访问性
- [ ] 支持键盘导航
- [ ] 图片有 alt 文本
- [ ] 对比度符合 WCAG AA 标准
```

## 边界场景和异常处理

**必须考虑的场景:**

```markdown
## 用户注册 - 边界和异常场景

### 输入边界
- [ ] 手机号格式错误 → 提示"请输入正确的手机号"
- [ ] 密码长度 < 8 位 → 提示"密码至少 8 位"
- [ ] 密码长度 > 20 位 → 提示"密码最多 20 位"
- [ ] 密码只有数字 → 提示"密码必须包含字母和数字"

### 业务边界
- [ ] 手机号已注册 → 提示并引导登录
- [ ] 验证码错误 3 次 → 要求重新获取
- [ ] 验证码过期 → 提示重新获取
- [ ] 同一手机号今日验证码次数达上限 → 提示"今日验证码次数已用完"

### 系统异常
- [ ] 短信服务故障 → 提示"验证码发送失败,请稍后重试"
- [ ] 数据库连接失败 → 提示"系统繁忙,请稍后重试"
- [ ] 网络超时 → 提示"网络超时,请检查网络连接"

### 并发场景
- [ ] 同一手机号同时注册 → 只创建一个账号
- [ ] 高并发下系统稳定 → 压测验证
```

## 测试用例

验收标准可以直接转化为测试用例:

```markdown
## 测试用例: 用户手机号注册

### 用例 1: 正常注册流程
**前置条件:** 手机号未注册
**测试步骤:**
1. 输入手机号 13800138000
2. 输入密码 Test1234
3. 点击"获取验证码"
4. 输入收到的验证码
5. 点击"注册"

**预期结果:**
- 注册成功
- 自动登录
- 跳转到首页

### 用例 2: 手机号已注册
**前置条件:** 手机号已注册
**测试步骤:**
1. 输入已注册手机号
2. 点击"获取验证码"

**预期结果:**
- 提示"该手机号已注册,请直接登录"
- 显示"去登录"按钮

### 用例 3: 验证码错误
**前置条件:** 手机号未注册
**测试步骤:**
1. 输入手机号
2. 获取验证码
3. 输入错误验证码
4. 点击"注册"

**预期结果:**
- 提示"验证码错误,请重新输入"
- 注册失败

### 用例 4: 密码强度不足
**前置条件:** 手机号未注册
**测试步骤:**
1. 输入手机号
2. 输入纯数字密码 12345678
3. 点击"注册"

**预期结果:**
- 提示"密码必须包含字母和数字"
- 注册失败
```

## 验收流程

### 1. 开发自测

开发完成后,开发人员根据验收标准自测:
- [ ] 功能完整性
- [ ] 正常流程
- [ ] 异常处理
- [ ] 边界场景

### 2. 测试验收

测试人员根据验收标准编写测试用例并执行:
- [ ] 功能测试
- [ ] 性能测试
- [ ] 安全测试
- [ ] 兼容性测试

### 3. 产品验收

产品经理验收:
- [ ] 功能符合需求
- [ ] 用户体验良好
- [ ] 无明显 bug
- [ ] 满足上线标准

### 4. 用户验收 (UAT)

邀请真实用户测试:
- [ ] 功能可用
- [ ] 体验良好
- [ ] 符合预期

## 常见问题

### 验收标准过于宽泛

❌ **不好的例子:**
```
- [ ] 系统性能良好
- [ ] 界面美观
- [ ] 用户体验好
```

✅ **好的例子:**
```
- [ ] API 响应时间 < 200ms (P95)
- [ ] 界面符合设计稿,误差 < 2px
- [ ] 用户完成注册流程时间 < 2 分钟
```

### 验收标准过于技术化

❌ **不好的例子:**
```
- [ ] 使用 Redis 缓存
- [ ] 使用 JWT 认证
- [ ] 使用 Docker 部署
```

✅ **好的例子:**
```
- [ ] 登录状态 7 天内有效
- [ ] 用户信息查询响应时间 < 100ms
- [ ] 系统可用性 99.9%
```

### 缺少异常场景

❌ **不完整:**
```
- [ ] 用户可以注册
- [ ] 用户可以登录
```

✅ **完整:**
```
- [ ] 用户可以注册
- [ ] 手机号已注册时提示
- [ ] 验证码错误时提示
- [ ] 网络异常时提示
- [ ] 用户可以登录
- [ ] 密码错误时提示
- [ ] 账号不存在时提示
```

## 最佳实践

✅ **推荐做法:**
- 验收标准在需求阶段就定义
- 与研发、测试一起评审验收标准
- 验收标准可量化、可测试
- 覆盖正常流程和异常场景
- 验收标准作为测试用例的基础

❌ **避免:**
- 验收标准过于模糊
- 只考虑正常流程
- 验收标准过于技术化
- 验收标准事后补充
