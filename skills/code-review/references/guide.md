# 代码审查指导文档

系统化的代码审查方法,帮助团队提升代码质量和可维护性。

## 代码审查清单

### 1. 代码规范

**命名规范:**
- ✅ 变量名清晰表达意图
- ✅ 函数名使用动词开头
- ✅ 类名使用名词,遵循大驼峰
- ✅ 常量使用全大写下划线分隔
- ❌ 避免单字母变量名(除循环变量)
- ❌ 避免拼音命名

**代码格式:**
- ✅ 统一的缩进(2空格或4空格)
- ✅ 合理的空行分隔
- ✅ 每行长度不超过 120 字符
- ✅ 导入语句按规范排序

### 2. 代码质量

**函数设计:**
- ✅ 单一职责原则
- ✅ 函数长度 < 50 行
- ✅ 参数数量 < 5 个
- ✅ 避免深层嵌套 (< 3 层)
- ✅ 提取重复代码

**错误处理:**
- ✅ 适当的异常处理
- ✅ 不吞没异常
- ✅ 有意义的错误信息
- ✅ 资源正确释放

**注释:**
- ✅ 复杂逻辑有注释说明
- ✅ 公共 API 有文档注释
- ✅ TODO 注释有负责人和日期
- ❌ 避免无用的注释
- ❌ 避免注释掉的代码

### 3. 安全性

**输入验证:**
- ✅ 所有外部输入都经过验证
- ✅ 防止 SQL 注入
- ✅ 防止 XSS 攻击
- ✅ 防止 CSRF 攻击

**敏感数据:**
- ✅ 密码加密存储
- ✅ 敏感数据传输加密
- ✅ 不在日志中记录敏感信息
- ✅ API 密钥不硬编码

**权限控制:**
- ✅ 适当的权限检查
- ✅ 最小权限原则
- ✅ 防止越权访问

### 4. 性能

**数据库:**
- ✅ 避免 N+1 查询
- ✅ 合理使用索引
- ✅ 避免全表扫描
- ✅ 使用连接池

**算法:**
- ✅ 时间复杂度合理
- ✅ 避免不必要的循环
- ✅ 合理使用缓存

**资源管理:**
- ✅ 及时释放资源
- ✅ 避免内存泄漏
- ✅ 合理的并发控制

### 5. 可测试性

- ✅ 代码易于测试
- ✅ 依赖可以 mock
- ✅ 避免全局状态
- ✅ 有单元测试覆盖

### 6. 可维护性

**代码结构:**
- ✅ 模块划分清晰
- ✅ 职责分离明确
- ✅ 依赖关系合理
- ✅ 避免循环依赖

**设计模式:**
- ✅ 合理使用设计模式
- ❌ 避免过度设计
- ❌ 避免过早优化

## 审查流程

### 1. 自审

开发者提交前自己审查:
- [ ] 代码符合规范
- [ ] 功能正常
- [ ] 测试通过
- [ ] 无明显问题

### 2. 同行评审

团队成员审查:
- [ ] 代码逻辑正确
- [ ] 符合设计要求
- [ ] 无安全隐患
- [ ] 性能可接受

### 3. 反馈和修改

- 提出具体的改进建议
- 解释问题原因
- 给出示例代码
- 跟踪修改情况

## 审查示例

**问题代码:**

```python
def get_user(id):
    user = db.query("SELECT * FROM users WHERE id = " + id)
    return user
```

**审查意见:**

❌ **安全问题**: SQL 注入风险
- 使用字符串拼接构建 SQL,存在注入风险
- 建议使用参数化查询

❌ **性能问题**: 查询所有字段
- SELECT * 查询了所有字段,可能包含不需要的大字段
- 建议只查询需要的字段

❌ **错误处理**: 缺少异常处理
- 数据库查询可能失败,缺少错误处理
- 建议添加 try-except

**改进后:**

```python
def get_user(user_id: int) -> Optional[User]:
    try:
        query = "SELECT id, username, email FROM users WHERE id = ?"
        user = db.query(query, (user_id,))
        return user
    except DatabaseError as e:
        logger.error(f"Failed to get user {user_id}: {e}")
        return None
```

## 最佳实践

✅ **推荐做法:**
- 及时审查,不积压
- 审查代码而非人
- 提供建设性意见
- 解释为什么,而非只说怎么做
- 认可好的代码

❌ **避免:**
- 过于苛刻或主观
- 只挑毛病不给建议
- 审查时间过长
- 忽视小问题
