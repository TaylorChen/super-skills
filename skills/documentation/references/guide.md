# 现代技术文档编写深度规范

旨在提升文档可读性、可维护性及专业度的全方位规范。

## 1. 文档结构体系

### 核心层级
- **README**: 项目门面, 包含简介、安装、快速开始及许可证。
- **用户手册 (User Guide)**: 面向非技术人员, 侧重核心功能操作流程。
- **API 参考 (API Reference)**: 详述接口地址、请求参数及响应码。
- **架构文档 (Architecture)**: 解释设计思路、组件依赖及数据流。
- **维护指南 (Maintenance)**: 环境搭建、测试运行及贡献流程。

## 2. 写作风格与语言 (Style Guide)

### 核心准则
- **主动语态**: "系统自动发送邮件" 优于 "邮件被系统自动发送"。
- **简洁性**: 删掉冗余词汇。一句话只传达一个关键意思。
- **一致性**: 专业术语全局统一。
- **解释代码**: 关键代码块前后必须有文字逻辑说明。

## 3. Markdown 与 MDC 语法强化

- **合理使用标题**: 语义化层级, 便于生成目录。
- **标注块 (Callouts)**: 使用 Note, Tip, Warning 区分信息权重。
- **Mermaid 图表**: 流程图、时序图的代码化维护。

## 4. API 文档自动化

- **OpenAPI / Swagger**: 基于 Spec 自动生成交互式文档。
- **JSDoc / TSDoc**: 通过注释自动提取函数及对象文档。

## 5. 持续维护策略 (Docs as Code)

- **文档版本化**: 随代码一同提交及打标签。
- **自动化校验**: 插件检测文档中的断链及拼写错误。
- **预览机制**: PR 提交后的文档预览链接。

## 6. 文档质量检查清单

- [ ] README 是否包含了 1 分钟即可上手的“快速开始”?
- [ ] 所有的示例代码是否在当前版本可以运行?
- [ ] 专业术语是否建立了统一的词汇表?
- [ ] 是否为所有的 API 参数提供了明确的类型详细说明?
